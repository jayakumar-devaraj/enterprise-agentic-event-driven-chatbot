# Latency and throughput rerun, 2026-10-24

Targets were pre-registered before any load, in `docs/reports/latency-targets-2026-10-24.md`
(commits `d2e99d0`, amended `ce46bc0` and `fa144be`, definition only). They are proposals for
the lead. **Every latency target fails, in both runs; error targets pass only for the real model.**
Raw per-request samples are in `latency-2026-10-24-mock.json` and `latency-2026-10-24-ollama.json`.

## Setup
- **Code:** the images were built from this PR's commit (current `main`, `801138e`, plus a
  `kafka.produce` span in the gateway producer that this measurement needs). Stack:
  `docker compose -f deploy/compose.yaml up -d --build --wait --scale worker=2 --scale gateway=2`.
- **Resources:** 2 gateways (1 CPU / 1.5 GB each), 2 workers (2 CPU / 1.5 GB each), Kafka (2 CPU /
  1 GB, 4 partitions), Redis, Qdrant, Jaeger. Ollama has 4 CPU / 3 GB, CPU only. Host: 12 logical
  CPUs, 15.7 GB RAM, Docker VM 8.3 GB. The LangFuse stack was stopped.
- **Load:** `tests/load/latency_a11.py`. One message per fresh thread (`"Why was I charged twice this
  month?"`), round-robin over both gateways, each client waiting for `done`.
- **Queue delay:** from Jaeger, the worker's `worker.process` start minus the gateway's
  `kafka.produce` start (the record handed to the Kafka client), in the same trace.
- **Host suspension:** the development machine enters Modern Standby when idle. A first real-model
  run spanned standby from 13:19 to 17:32 local (Windows Kernel-Power events 506/507), giving a
  15,221 s completion p95. It was discarded. The runs below held a `SetThreadExecutionState`
  keep-awake request, and their wall times match the clock.

## What the traces show (mock run of record)
Span durations from Jaeger for the same window:

| Span | p50 | p95 | Total |
|---|---|---|---|
| `POST /chat` (gateway) | 4414 ms | 6320 ms | 891.9 s |
| `kafka.produce` (inside POST) | 3911 ms | 5793 ms | 772.0 s |
| `worker.process` | 403 ms | 728 ms | 87.7 s |
| `route` | 190 ms | 384 ms | 40.2 s |
| `respond` | 107 ms | 210 ms | 25.0 s |

- **The gateway's Kafka produce dominates `POST /chat`** (89% of its median). Measured in isolation,
  outside the gateway, the same `KafkaEnvelopeProducer` takes a flat ~2.03 s per send at 1, 5 and
  20 concurrent sends, with no timeouts. Inside the loaded gateway it stretches to its 6 s timeout,
  and the `POST 503`s are exactly those timeouts: in the first run, 147 `kafka.produce` spans had
  error status, one per 503. A single unloaded probe showed the worker starting about 1 s
  *before* the gateway's produce call returned.
- **Workers are not saturated by message processing.** Traced processing totals 87.7 s across 2
  workers over 106 s (about 41%). Yet `docker stats` showed both workers near 100% CPU. That CPU is
  spent outside the traced spans, and the 44.7 s queue delay p95 is unexplained by span time.

## Not established (next experiments, in order)
1. Why the producer floor is about 2 s. The 2026-10-17 investigation found the async producer's
   1 s Python-side batching. Try a small positive `buffer_timeout` with `batch_size=1`, the
   variant that did not break delivery.
2. Why the produce call times out only inside the loaded gateway. Candidates, unverified: CPU
   contention on 1 CPU with scrypt and the scrubber, or thread-pool starvation of the producer's
   delivery handling.
3. Where worker CPU goes outside spans, and why queue delay far exceeds processing time. Profile a
   worker under this load, and record per-partition lag over time.
4. The 2 empty real-model replies.

No fix was attempted here. This report measures the system at this commit.
